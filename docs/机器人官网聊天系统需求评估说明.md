# 机器人官网聊天系统需求评估说明

## 1. 目的

本文用于评估《FF 官网智能服务机器人需求讨论》以及产品团队输出的 `BRD.md` 在当前项目中的落地可行性，重点回答以下问题：

- 需求讨论中的哪些能力已经被当前项目支持
- 哪些需求可以在现有架构上较低成本扩展
- 哪些能力当前缺少关键数据或系统支撑
- 在“保持现有交互形式不变、改动聚焦问答层”的前提下，推荐的开发方案是什么

补充说明：

- `BRD.md` 定义的是 FF 官网统一智能客服的业务目标，覆盖汽车、机器人、AIxC 三条业务线
- 当前项目实际基础是 `机器人产品文档站点 + 机器人 RAG 问答`
- 因此本评估会同时给出两个层面的判断：
  - 从集团官网客服 BRD 视角看，当前项目能承接什么
  - 从机器人业务单线落地视角看，下一阶段最合理的开发边界是什么

---

## 2. 当前项目现状

当前项目本质上是一个 `机器人产品手册站点 + RAG 问答系统`，不是完整的 FF 官网客服系统。

### 2.1 已有能力

- 前端已有固定聊天入口与 ChatKit 对话面板
- 后端已有 `Triage Agent -> Support Agent` 的两段式问答链路
- 已接入 OpenAI Vector Store，可基于文档进行 RAG 检索回答
- 已支持多产品识别与分产品知识库路由
- 已支持回答引用来源跳转到对应文档页面
- 已支持跨页面语义搜索

### 2.2 当前知识范围

当前后台 Agent 的核心知识主要来自四类机器人产品说明书：

- `FF Master Ultra`
- `FF Futurist Ultra`
- `FF Aegis Ultra`
- `FF Aegis EDU`

这些说明书主要覆盖：

- 产品概述
- 参数规格
- 开关机与充电
- 遥控器、APP、OTA
- 维护保养
- 故障排查
- 运输与存储
- 保修说明

### 2.3 当前系统定位

从能力边界上看，当前系统更接近：

`机器人产品说明书问答助手`

而不是：

`机器人官网智能客服 / 官网转化助手`

这意味着，当前系统已经能回答“怎么用”，但还不够支持“怎么选、怎么约、怎么联系、怎么转人工、怎么形成官网转化闭环”。

### 2.4 与 BRD 的关系判断

`BRD.md` 目标是建设一个覆盖 `汽车 + 机器人 + AIxC` 的统一官网客服入口，而当前项目只能直接承接其中的 `机器人业务问答底座`。

因此当前项目在 BRD 全局中的角色，更适合定义为：

`FF 官网统一智能客服的一期子能力：机器人业务知识问答与售前引导模块`

它不是 BRD 的完整实现，但可以作为后续官网统一客服系统的一个先行能力模块。

## 3. 需求讨论的核心诉求拆解

结合《需求讨论》与 `BRD.md`，机器人官网聊天系统相关需求可以拆成 6 类。

### 3.1 官网公开问答

面向官网访客，回答机器人相关的公开信息：

- 产品介绍
- 参数规格
- 使用方式
- 维护保养
- 故障排查
- 保修与联系方式

### 3.2 售前咨询与推荐

面向潜在客户，提供：

- 产品差异对比
- 场景适配推荐
- 选型建议
- 企业咨询引导

### 3.3 官网动作闭环

用户咨询后，应能继续进入官网动作：

- 查看详情
- 预约体验
- 联系销售
- 联系售后
- 留资转人工

### 3.4 智能检索体验

包括：

- 关键词搜索
- 联想推荐
- 相关问题推荐
- 命中内容高亮

### 3.5 风险控制与边界管理

包括：

- 超范围问题兜底
- 未公开信息禁答
- 商务与价格边界
- 投资、Web3、汽车等非机器人话题拦截

### 3.6 运营闭环与数据沉淀

这是 BRD 新增后需要特别强调的一类需求，包括：

- 用户评价机制
- 热点问题统计
- 问题分类与解决率统计
- 人工转接率统计
- 咨询数据结构化存储
- 为后续产品优化与运营决策提供分析基础

## 4. BRD 对齐评估

从 `BRD.md` 定义的 `BR-1` 到 `BR-8` 看，当前项目与目标能力的匹配关系如下。

| BRD 需求 | 当前项目匹配度 | 说明 |
|------|------|------|
| BR-1 多业务统一咨询入口 | 低 | 当前仅有机器人业务知识，不支持汽车和 AIxC |
| BR-2 7×24 小时自助服务 | 中 | 技术上可以 7×24 提供机器人问答，但业务覆盖不足 |
| BR-3 智能人工转接 | 低 | 目前没有人工转接规则、留资字段和入口配置 |
| BR-4 知识库全覆盖 | 低到中 | 机器人说明书覆盖较好，但不覆盖汽车、AIxC、官网流程 |
| BR-5 跨业务上下文保持 | 低 | 当前上下文主要用于机器人单业务会话，未实现跨业务语义切换 |
| BR-6 合规与风控 | 中 | 已可通过 prompt 和 triage 控制范围，但缺法务审核内容与系统级规则配置 |
| BR-7 用户反馈机制 | 低 | 当前无显式点赞/点踩和反馈沉淀 |
| BR-8 数据沉淀与分析 | 低到中 | 当前有日志和会话记录基础，但缺结构化分析口径与指标体系 |

结论：

- 从 BRD 全局目标看，当前项目只能部分支撑 `BR-2 / BR-4 / BR-6`，且仅限机器人业务
- 如果把范围收敛到机器人官网场景，当前项目可以作为一个较好的 `Phase 1` 起点
- 如果直接要求当前项目承接 BRD 全部范围，则会出现明显的业务范围和数据范围错位

## 5. 需求适配评估

### 5.1 已具备或基本具备的能力

以下需求，当前项目已经具备基础能力，或者仅需提示词与知识库调整即可实现。

| 需求项 | 当前状态 | 评估 |
|------|------|------|
| 机器人产品公开问答 | 已具备 | 当前说明书 RAG 已可覆盖参数、使用、故障、保修等问题 |
| 多产品识别与路由 | 已具备 | 已有 triage 识别产品并路由到对应知识库 |
| 回答引用跳转 | 已具备 | 当前支持从回答引用跳转到相关页面 |
| 官网问答范围收敛 | 已具备基础 | 已可通过 triage 和 prompt 限制到机器人官网范围 |
| 跨产品通用问答 | 部分具备 | general agent 已支持，但仍偏“手册型回答” |
| 关键词搜索/语义搜索 | 已具备基础 | 现有搜索能力可复用到聊天联想和结果召回 |

### 5.2 可在现有架构上较快扩展的能力

以下需求不需要推翻现有系统，但需要补充数据和路由策略。

| 需求项 | 当前状态 | 缺口 | 评估 |
|------|------|------|------|
| 产品差异对比 | 部分具备 | 缺官网版对比知识 | 可基于结构化对比表快速补齐 |
| 产品选型建议 | 部分具备 | 缺场景推荐数据 | 适合通过 FAQ + 规则路由实现 |
| 官网相关推荐 | 部分具备 | 缺运营配置与 FAQ 关联 | 可在回答后增加推荐问题 |
| 联系方式问答 | 部分具备 | 缺官网统一联系方式数据 | 适合配置化管理 |
| 人工转接话术 | 部分具备 | 缺转人工规则与入口数据 | 可快速实现 |
| FAQ 型售前问答 | 部分具备 | 缺官网售前 FAQ | 非常适合补到知识库 |
| 用户反馈机制 | 部分具备 | 缺前端反馈入口和后端存储 | 低成本可补 |
| 咨询数据统计 | 部分具备 | 缺结构化埋点与报表口径 | 可先从后端结构化日志开始 |

### 5.3 当前无法仅靠说明书实现的能力

以下需求如果没有新增数据或系统对接，当前项目无法可靠实现。

| 需求项 | 原因 |
|------|------|
| 预约体验 | 当前没有预约入口、动作配置、表单或接口数据 |
| 联系销售/售后闭环 | 当前没有统一的官网动作配置与转接规则 |
| 企业定制咨询 | 当前没有企业场景资料、方案模板、商务入口 |
| 场景化方案推荐 | 说明书缺少“场景 -> 推荐产品 -> 推荐理由”结构化数据 |
| 价格、预订、采购相关问答 | 当前说明书通常不包含官网公开价格或商务口径 |
| 热门问题联想与推荐优化 | 当前缺少搜索日志、问题统计、运营词表 |
| 个性化推荐 | 当前没有用户画像、行为记录和策略引擎 |
| 跨系统订单/CRM/售后状态查询 | 当前没有业务系统打通 |
| 集团级统一客服入口 | 当前项目没有汽车、AIxC 知识体系与路由体系 |

## 6. 为实现需求讨论与 BRD，还需要哪些数据支持

当前项目最核心的缺口不是模型能力，而是 `官网业务数据` 不足。

### 6.1 官网售前 FAQ 数据

用于支撑：

- 产品卖点介绍
- 型号差异对比
- 选型建议
- 高频售前问答

建议数据内容：

- 产品定位
- 目标用户
- 适用场景
- 核心卖点
- 常见问题及标准答案
- 官网详情页链接

### 6.2 产品对比与选型数据

用于支撑：

- “哪款适合展厅/教育/科研/接待”
- “Aegis 与 Futurist 有什么区别”
- “如何选择不同型号”

建议数据内容：

- 产品维度对比表
- 场景推荐表
- 不推荐场景说明
- 推荐理由

### 6.3 官网动作与转化数据

用于支撑：

- 预约体验
- 联系销售
- 联系售后
- 留资与人工转接

建议数据内容：

- 动作名称
- 动作类型
- 对应入口 URL
- 适用产品范围
- 适用地区
- 是否启用

### 6.4 联系方式与服务流程数据

用于支撑：

- 售后怎么联系
- 遇到问题该怎么处理
- 联系谁、通过什么方式联系

建议数据内容：

- 服务类型
- 受理范围
- 联系方式
- 服务时段
- 所需材料
- 处理流程

### 6.5 运营与检索优化数据

用于支撑：

- 联想推荐
- 热门问题
- 无结果兜底
- 相关推荐

建议数据内容：

- 热门问题库
- 同义词词表
- 高转化问题模板
- 搜索日志
- 未命中问题列表

### 6.6 风控与边界规则数据

用于支撑：

- 未公开信息不回答
- 商务与价格类问题兜底
- 非机器人问题拦截

建议数据内容：

- 可回答主题清单
- 禁答主题清单
- 标准兜底话术
- 必须转人工的意图规则

### 6.7 用户反馈与分析数据

这是 BRD 相比原始需求讨论更明确强调的一块，建议单独建设。

用于支撑：

- 回答有用/无用反馈
- AI 独立解决率
- 热门问题识别
- 解决率与转人工率分析
- 后续知识库迭代优先级判断

建议数据内容：

- 会话 ID
- 用户问题分类
- 命中知识类型
- 是否解决
- 是否转人工
- 反馈结果
- 所属业务线
- 所属产品
- 时间、终端、来源页面

### 6.8 法务与业务审核数据

由于 BRD 明确强调 AIxC 合规、知识准确性和品牌风险，因此从系统设计上需要保留“审核后的可发布口径”。

即使当前阶段先只做机器人业务，也建议数据模型预留如下字段：

- 内容所属业务部门
- 内容审核状态
- 审核人
- 审核时间
- 生效时间
- 过期时间
- 风险等级

这样后续扩展到汽车和 AIxC 时，不需要重构知识治理方式。

## 7. 结合当前项目的开发判断

### 7.1 不建议做的事情

在当前阶段，不建议直接做以下重型能力：

- 多模态图片问答
- 语音输入
- 个性化推荐
- CRM/订单系统打通
- 商务流程自动化
- 通用聊天能力扩展

原因不是做不到，而是当前项目的主要短板并不在模型或交互，而在于官网业务数据缺失。如果数据层没补齐，继续扩展模型能力的收益有限。

### 7.2 建议优先做的方向

建议优先把当前系统升级为：

`机器人官网公开信息问答 + 售前引导 + 数据沉淀助手`

也就是先完成以下目标：

- 从“说明书问答”升级为“官网机器人问答”
- 把售前 FAQ、产品对比、场景推荐补进知识层
- 给回答补充明确的下一步动作
- 对超范围、无公开信息、需人工介入的问题形成稳定兜底
- 给每次问答补上可分析的数据记录和反馈入口

## 8. 推荐开发方案

在保持现有聊天交互不变的前提下，建议采用“四层增强”方案。

### 8.1 第一层：知识层补齐

新增一批更适合官网客服场景的知识文件，而不是只依赖说明书。

建议新增内容：

- `robot-website-faq.md`
- `robot-product-comparison.md`
- `robot-scenarios.md`
- `robot-sales-contact.md`
- `robot-after-sales.md`
- `robot-handoff-rules.md`

建议落位：

- 非结构化 FAQ 和说明：放入 `src/content/pages/` 或独立知识目录，并同步到 Vector Store
- 结构化配置数据：以 JSON 文件放在 `src/content/` 或 `apps/rag-api/app/data/`

### 8.2 第二层：问答路由层增强

基于现有 `triage -> support agent` 架构，增加更明确的意图分流。

建议增加的意图类型：

- 产品介绍
- 参数规格
- 使用帮助
- 故障排查
- 产品对比
- 场景推荐
- 联系方式
- 转人工
- 超范围

路由原则：

- 能走结构化规则和配置的，优先走结构化答案
- FAQ 和场景问题优先命中官网知识库
- 手册型问题继续走当前产品说明书 RAG
- 超范围和无公开信息问题走固定兜底

### 8.3 第三层：回答层增强

将回答统一成“答案 + 下一步动作”的格式。

建议输出结构：

1. 简短结论
2. 关键信息点
3. 若有资料则给引用
4. 若有下一步动作则给出：
   - 查看详情
   - 联系销售
   - 联系售后
   - 留资转人工

这样可以让聊天系统从“回答问题”升级为“官网转化助手”。

### 8.4 第四层：反馈与分析层增强

为对齐 BRD 的 `BR-7` 和 `BR-8`，建议在现有后端基础上补齐最小可用的数据闭环。

建议新增能力：

- 对每轮回答记录结构化分类结果
- 增加用户反馈字段：有用 / 无用
- 记录是否命中 FAQ、结构化规则、说明书 RAG
- 记录是否触发转人工或建议联系人工
- 生成基础统计指标：
  - 问题量
  - 热门意图
  - 未命中率
  - 转人工率
  - 用户反馈率

这一步不要求一开始就做完整 BI 平台，但需要先把数据模型设计正确。

## 9. 分阶段实施建议

### Phase 1：机器人官网问答升级

目标：从说明书问答升级为官网机器人问答。

工作项：

- 调整 triage 和 prompt 范围边界
- 新增官网 FAQ 知识文件
- 新增对比与选型知识文件
- 完善超范围与无信息兜底
- 增加最小结构化日志字段

产出：

- 可稳定回答机器人官网公开问题
- 可处理基础选型和跨产品比较
- 为后续统计打下数据基础

### Phase 2：机器人业务动作闭环

目标：让回答能落到明确动作。

工作项：

- 增加联系销售/售后/预约等动作配置
- 统一回答中的 CTA 输出
- 加入人工转接规则
- 增加有用/无用反馈入口与存储

产出：

- 可形成“咨询 -> 行动”的闭环
- 可统计基础解决率和转人工情况

### Phase 3：运营与效果优化

目标：提升命中率和转化率。

工作项：

- 加入热门问题与联想词
- 加入未命中问题统计
- 持续补 FAQ 和场景库
- 建立问答评测集

产出：

- 问答质量可持续优化
- 可通过数据驱动迭代

### Phase 4：向 BRD 全局目标扩展

目标：从机器人业务单线能力，扩展到 FF 官网统一客服框架。

工作项：

- 抽象统一的多业务 triage 模型
- 引入汽车业务知识库与流程数据
- 引入 AIxC 合规知识与法务审核机制
- 建设跨业务上下文保持能力
- 对接统一的人工客服与留资系统

产出：

- 与 BRD 对齐的集团级官网智能客服框架
- 机器人项目从“试点模块”升级为“统一客服中的一个业务域”

## 10. 推荐的项目改造点

### 10.1 后端

重点改造 `apps/rag-api`：

- `triage`：增加意图分类与官网范围控制

## 11. 结论

结合当前项目现状，可以得出以下结论：

1. `BRD.md` 定义的是 FF 官网统一智能客服的集团级目标，而当前项目只能直接承接其中的机器人业务模块，不能等同于 BRD 的完整实现。
2. 当前项目已经具备机器人官网聊天系统的基础骨架，尤其是聊天面板、分产品问答、RAG 检索、引用跳转和语义搜索能力。
3. 需求讨论与 BRD 中的“机器人官网公开问答”部分，大量能力可以在现有架构上直接实现或低成本扩展。
4. 当前最大的短板不是模型，而是官网业务数据不足，特别是售前 FAQ、产品对比、场景推荐、联系方式、动作入口、转人工规则、反馈数据和审核机制。
5. 最合适的开发路径，不是重做交互，而是在现有项目上补齐知识层、增强问答路由、增加官网动作闭环，并从第一阶段开始建设数据沉淀能力。
6. 推荐先完成 `机器人官网问答升级 -> 机器人业务动作闭环 -> 运营优化 -> 向 BRD 全局扩展` 四阶段迭代，而不是一开始就做多模态、个性化和跨系统集成。

最终建议将本项目下一阶段的目标定义为：

`面向机器人官网公开信息、售前引导和数据沉淀的智能问答系统`

并将其定位为：

`FF 官网统一智能客服 BRD 的机器人业务先行模块`
