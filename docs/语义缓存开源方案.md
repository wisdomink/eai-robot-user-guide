# RAG FAQ Acceleration - Open Source Solution Selection

## 1. 背景

当前系统是一个面向 FF Robot / FF 91 用户手册的 H5 + AI 问答系统，已有能力包括：

- Markdown 用户手册内容站；
- 全站语义搜索；
- ChatKit 对话面板；
- 多 Agent RAG 问答；
- 引用跳转；
- 聊天历史查询；
- Admin 配置后台；
- 首页推荐、场景推荐、留资配置。

当前用户反馈的问题是：**查询速度慢**。

产品提出的优化方向是：

1. 准备一个问答库，如果用户问题命中已有问题，直接返回预制答案；
2. 记录用户问答，如果某个问题被重复提到超过阈值，则进入预制问题候选库；
3. 用户后续提问时，优先匹配预制库，命中后避免大模型参与，降低耗时。

本质上，这是在现有 RAG 前面增加一层：

```text
FAQ 命中层 + 语义缓存层 + 高频问题沉淀层
```

当前系统本身已有 RAG、语义搜索和 ChatKit 能力，因此不建议重做完整客服机器人系统，而是应该采用“轻量开源组件 + 自建业务逻辑”的方式增强现有架构。

---

## 2. 需要解决的问题

### 2.1 性能问题

当前 RAG 问答链路可能包括：

```text
用户问题
  ↓
产品识别
  ↓
意图判断
  ↓
向量检索
  ↓
Agent 编排
  ↓
大模型生成
  ↓
引用映射
  ↓
流式返回
```

这个流程准确性较高，但对高频、简单、重复问题来说过重。

例如：

- “FF Master 怎么充电？”
- “怎么连接 Wi-Fi？”
- “如何恢复出厂设置？”
- “机器人无法开机怎么办？”

这些问题不需要每次都进入 RAG 和大模型。

### 2.2 问答库问题

需要区分两类问题：

```text
上下文无关问题：
单独一句话就能理解，可以进入 FAQ 问答库。

上下文相关问题：
依赖前文中的“它、这个、刚才那个、上面说的型号”等信息，不应该直接进入 FAQ。
```

FAQ 库中应该只保存标准化后的上下文无关问题。

### 2.3 高频问题沉淀问题

用户问法通常不完全一致，例如：

```text
FF Master 怎么充电？
FF Master 如何充电？
机器人怎么充电？
这个机器狗充电方式是什么？
充电底座怎么用？
```

不能只按字符串完全相同统计，而应该基于语义相似度进行聚类。

## 3. 开源方案清单

## 3.1 GPTCache

### 3.1.1 项目定位

GPTCache 是 Zilliz 开源的 LLM 语义缓存库，定位是为 LLM 查询创建语义缓存。它可以通过 embedding 对用户问题做语义匹配，然后复用历史 LLM 响应。

### 3.1.2 适合解决的问题

适合解决：

```text
相似问题重复调用大模型的问题
```

例如：

```text
用户 A：FF Master 怎么充电？
用户 B：FF Master 如何连接充电底座？
```

如果语义相似度足够高，可以直接复用已有答案。

### 3.1.3 接入位置

建议放在现有 RAG 前面：

```text
用户问题
  ↓
FAQ 精确匹配
  ↓
FAQ 语义匹配
  ↓
GPTCache 语义缓存
  ↓
原 RAG / ChatKit
```

### 3.1.4 优点

| 优点 | 说明 |
|---|---|
| 面向 LLM 缓存 | 直接解决重复问题复用答案 |
| 支持语义相似 | 不要求问题文本完全一致 |
| 后端可选 | 可接 FAISS / Milvus / Zilliz |
| Python 生态友好 | 适合接入当前 RAG 后端 |

### 3.1.5 缺点

| 缺点 | 说明 |
|---|---|
| 更像缓存，不是正式 FAQ 系统 | 不适合直接作为可运营问答库 |
| 需要控制误命中 | 相似问题不一定能共用答案 |
| 上下文问题风险高 | 不能直接缓存“它怎么操作”这类问题 |
| 需要人工治理 | 缓存答案可能过期或不准确 |

### 3.1.6 推荐结论

GPTCache 适合作为：

```text
历史问答语义缓存层
```

但不建议作为：

```text
正式 FAQ 问答库
```

正式 FAQ 仍然应该由业务表、后台审核和版本管理控制。

## 3.2 Redis + LangChain RedisSemanticCache

### 3.2.1 项目定位

Redis 生态中，LangChain Redis 提供 RedisCache 和 RedisSemanticCache。RedisCache 用于传统 key-value 精确缓存，RedisSemanticCache 使用 Redis 和向量相似搜索实现语义缓存。

### 3.2.2 适合解决的问题

适合同时解决：

```text
精确问题缓存
语义相似问题缓存
热点问题计数
用户问题日志
限流与短期缓存
```

### 3.2.3 接入位置

Redis 可以做多层能力：

```text
Redis String / Hash：精确 FAQ 缓存
Redis Vector：语义缓存
Redis Sorted Set：热点问题统计
Redis Stream / List：问题日志队列
```

### 3.2.4 优点

| 优点 | 说明 |
|---|---|
| 性能高 | 非常适合低延迟命中 |
| 工程成熟 | 运维简单，生态成熟 |
| 可同时做缓存和统计 | 一套 Redis 可以覆盖多个场景 |
| 接入成本低 | 比完整客服框架轻很多 |

### 3.2.5 缺点

| 缺点 | 说明 |
|---|---|
| 业务逻辑要自建 | FAQ 审核、上下架、候选库需要自己做 |
| 语义检索能力不如专业向量库灵活 | 复杂过滤和多 collection 管理不如 Qdrant |
| 长期知识治理不适合只放 Redis | 正式 FAQ 仍建议落数据库 |

### 3.2.6 推荐结论

Redis 是最适合当前项目的基础组件之一。

推荐用法：

```text
Redis 做缓存、计数、热点统计；
数据库做正式 FAQ 和候选 FAQ；
Qdrant 或 Redis Vector 做语义匹配。
```

## 3.3 Qdrant

### 3.3.1 项目定位

Qdrant 是开源向量搜索引擎和向量数据库，支持向量相似度搜索、payload 过滤、结构化条件筛选等能力。

### 3.3.2 适合解决的问题

适合做：

```text
正式 FAQ 语义匹配库
候选问题聚类库
用户问题向量日志库
产品维度过滤
语言维度过滤
场景维度过滤
```

### 3.3.3 推荐 collection 设计

```text
collection: faq_official
  - 标准问题
  - 相似问法
  - 答案
  - 产品
  - 来源页面
  - 状态
  - 版本

collection: faq_candidate
  - 代表问题
  - 相似原始问题
  - 出现次数
  - 建议答案
  - 审核状态

collection: query_memory
  - 用户原始问题
  - 改写后问题
  - 产品
  - 命中来源
  - 时间
```

### 3.3.4 优点

| 优点 | 说明 |
|---|---|
| 语义匹配能力强 | 适合 FAQ 语义检索 |
| payload 过滤方便 | 可按产品、语言、状态、场景过滤 |
| 比 Redis Vector 更适合长期向量资产 | 正式库、候选库都可管理 |
| 自部署友好 | 开源，可 Docker 部署 |
| 高并发性能好 | Rust 实现，适合生产使用 |

### 3.3.5 缺点

| 缺点 | 说明 |
|---|---|
| 需要额外部署 | 比纯 Redis 多一个组件 |
| 业务管理能力要自建 | Admin、审核、发布流程需要自己实现 |
| 阈值需要评测调优 | 不同问题类型需要不同相似度阈值 |

### 3.3.6 推荐结论

如果做最终版本，Qdrant 很适合作为：

```text
FAQ 语义匹配中心
候选问题聚类中心
问题向量分析中心
```

推荐优先级很高。

## 3.4 Semantic Router

### 3.4.1 项目定位

Semantic Router 是一个开源语义路由库，定位是为 LLM 和 Agent 提供快速决策层。它通过语义向量空间进行请求路由，避免等待慢速 LLM 来做工具选择或路由判断。

### 3.4.2 适合解决的问题

适合做：

```text
问题进入 FAQ
问题进入 RAG
问题进入留资
问题进入人工客服
问题进入拒答
问题进入澄清
```

### 3.4.3 接入位置

```text
用户问题
  ↓
上下文改写
  ↓
Semantic Router
  ├── faq_route
  ├── rag_route
  ├── lead_capture_route
  ├── troubleshooting_route
  ├── safety_route
  └── fallback_route
```

### 3.4.4 优点

| 优点 | 说明 |
|---|---|
| 适合多路径路由 | 当前系统已有推荐、留资、RAG，适合统一分流 |
| 比 LLM 判断快 | 可降低路由耗时 |
| 易于扩展 | 后续可增加人工客服、工单、售后等 route |
| 适合 Agent 前置层 | 避免所有问题都进入重 Agent 流程 |

### 3.4.5 缺点

| 缺点 | 说明 |
|---|---|
| 不是 FAQ 库 | 只能路由，不能替代问答库 |
| 不是缓存系统 | 不能替代 GPTCache / Redis |
| 阈值和 route 样本需要维护 | 需要持续调优 |

### 3.4.6 推荐结论

Semantic Router 适合作为最终版本的：

```text
智能路由层
```

不建议作为第一核心组件，但最终架构中值得加入。

## 3.5 Rasa FAQ / ResponseSelector

### 3.5.1 项目定位

Rasa 是传统对话机器人框架。Rasa 有 FAQ 和 chitchat 处理方式，用于处理上下文无关的 FAQ 和闲聊问题。

### 3.5.2 适合解决的问题

适合：

```text
传统 FAQ 机器人
意图识别
固定回复
闲聊回复
规则流程
```

### 3.5.3 优点

| 优点 | 说明 |
|---|---|
| FAQ 能力成熟 | 有完整 FAQ / chitchat 体系 |
| 对话系统完整 | intent、rules、stories、actions 都有 |
| 可私有部署 | 适合企业内部客服机器人 |

### 3.5.4 缺点

| 缺点 | 说明 |
|---|---|
| 架构较重 | 当前系统已有 ChatKit + RAG，不需要再引入完整机器人框架 |
| 接入成本高 | 要维护 Rasa 自己的训练数据和配置 |
| 与现有 Agent 架构重叠 | 容易形成两套对话系统 |
| 不适合作为轻量加速层 | 为了解决 FAQ 命中引入 Rasa 过重 |

### 3.5.5 推荐结论

Rasa 能做，但不推荐接入当前项目。

适合场景：

```text
未来要做完整客服机器人平台
需要复杂多轮流程管理
需要替代当前 ChatKit / Agent 架构
```

当前阶段不建议使用。

## 4. 推荐选型对比

| 方案 | 适合用途 | 是否推荐 | 推荐位置 |
|---|---|---:|---|
| Redis | 精确缓存、计数、热点统计、短期缓存 | 强推荐 | 基础缓存层 |
| Qdrant | FAQ 语义匹配、候选问题聚类 | 强推荐 | 向量匹配层 |
| GPTCache | 历史问答语义缓存 | 推荐 | RAG 前置缓存层 |
| Semantic Router | 问题分流、路由判断 | 推荐 | Agent 前置路由层 |
| Rasa | 完整 FAQ 机器人 | 不推荐 | 除非重做客服系统 |

---

## 5. 最终推荐组合

### 5.1 推荐开源组件组合

```text
Redis
  - 精确 FAQ 缓存
  - 热点问题计数
  - 查询日志缓冲
  - 短期语义缓存

Qdrant
  - 正式 FAQ 向量库
  - 候选 FAQ 向量库
  - 用户问题聚类库

GPTCache
  - 历史 LLM 答案语义缓存
  - 减少重复 RAG 调用

Semantic Router
  - FAQ / RAG / 留资 / 澄清 / 拒答分流
```

### 5.2 不推荐引入

```text
Rasa
```

原因：

```text
当前项目不是传统客服机器人，而是用户手册内容站 + RAG + ChatKit。
引入 Rasa 会造成架构重叠和维护成本上升。
```

---

## 6. 最终技术结论

当前项目最合适的开源方案不是单一框架，而是组合式架构：

```text
Redis + Qdrant + GPTCache + Semantic Router
```

其中：

```text
Redis 负责快；
Qdrant 负责准；
GPTCache 负责省；
Semantic Router 负责分流；
现有 RAG 负责复杂问题兜底。
```

最终目标是：

```text
简单问题不进大模型；
重复问题不进大模型；
高频问题沉淀为标准 FAQ；
上下文问题先改写，再匹配；
复杂问题继续走原有 RAG。
```
