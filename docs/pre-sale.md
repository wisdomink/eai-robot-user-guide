目标不是硬推销，而是三件事：
1. 在用户最可能需要时，推荐“相关机器人产品” 
2. 在用户完成当前任务的前后，推荐“有价值的新功能点” 
3. 用尽量低打扰的方式，提升转化、功能发现率和留存 

---
一、先定义：推荐系统到底推荐什么
现有的场景里，推荐内容建议分成两大类。
1）产品推荐
适合做“产品匹配 / 升级引导 / 跨产品引流”
例如：
-  当前用户在看 Aegis EDU，但提问越来越偏工业巡检，可以推荐 Aegis Ultra 
-  当前用户频繁问高阶能力、性能、部署方式，可以推荐更高阶产品线 
-  用户是通用搜索流量进入，没有明确产品归属，可以先做产品分流推荐 
2）功能推荐
适合做“新能力发现 / 功能教育 / 使用深挖”
例如：
-  用户刚问完“怎么搜索文档”，可以推荐“语义搜索” 
-  用户多次追问同一故障定位，可以推荐“引用跳转”“历史对话”“相关文档入口” 
-  上线了新的 Agent 能力、搜索能力、FAQ 能力后，做定向曝光 
从产品设计上，这两类内容不要混成一个池子。应该在后台配置时区分为：
- product_reco
- feature_reco
因为它们的触发逻辑、文案、目标行为、评估指标都不同。

---
二、推荐应该在什么时候出现
这个是核心。推荐系统成败，不在“推荐内容多不多”，而在“时机对不对”。
按用户行为阶段来做，而不是按页面位置来做。
场景 A：用户刚进入 ChatPanel，但还没提问
这是最轻的冷启动时机。
适合推荐：
-  热门提问入口 
-  当前页面相关功能 
-  当前产品常见问题 
-  新功能点的轻提示 
形式建议：
-  输入框上方 1 条“轻卡片” 
-  输入框内预置 suggestion chips 
这时候不要直接推产品，更适合推“怎么开始用”。

---
场景 B：用户刚提了一个问题，但系统还没回答
这是“意图识别”最重要的窗口。
如果 Triage Agent 已经识别出：
-  产品归属不明确 
-  用户意图偏选型 
-  当前提问和当前页面/当前产品不匹配 
就可以在回答前或回答顶部做辅助型推荐：
比如：
你提到的是“多机协同巡检”，这个更接近 Aegis Ultra 的能力范围。是否了解一下对应产品说明？
形式建议：
-  回答上方插入一条 system recommendation card 
-  或回答底部附一条“你可能更需要” 
这个阶段的推荐是“纠偏型”，价值非常高。

---
场景 C：回答完成后，用户大概率还有下一步
这是最适合做推荐的主时机。
因为用户刚获得一个答案，认知负担最低，也最容易接受“下一步建议”。
适合推荐：
-  相关功能点 
-  下一步操作 
-  相关产品能力 
-  文档入口 
例子：
-  用户问“如何搜索手册内容” → 回答后推荐“试试语义搜索” 
-  用户问“这个机器人支不支持某能力” → 回答后推荐“查看该产品参数页 / 对比另一款产品” 
-  用户问“安装配置怎么做” → 回答后推荐“引用跳转到安装章节” 
形式建议：
- 回答底部 1 张推荐卡
-  或 2 个横向 action chips：“查看功能”“了解相关产品” 
这是系统里最应该重点做的推荐位。

---
场景 D：用户连续追问 2～3 次同一主题
这说明单次回答没有完全满足，或者用户在做更深任务。
这时推荐的重点不是曝光，而是“帮助完成任务”。
适合推荐：
-  更强的功能入口 
-  更完整的产品能力 
-  专题页/对比页 
-  新功能点的解决方案式推荐 
比如：
-  连续问 3 次部署 → 推荐“部署指南专题” 
-  连续问 2 次多语言搜索 → 推荐“语义搜索” 
-  连续问某高阶能力，而当前产品不支持 → 推荐更适合的机器人产品 
形式建议：
-  不要弹窗 
-  用“连续追问识别后”的增强卡片 
-  文案语气偏助手型，而不是营销型 

---
场景 E：回答低置信度、检索结果差、没有命中
这是“救场型推荐”。
如果系统出现：
-  未检索到高质量引用 
-  回答置信度低 
-  用户问题超出当前产品手册范围 
应该立刻转向推荐，而不是继续硬答。
适合推荐：
-  更合适的产品线 
-  通用支持 Agent 
-  相关手册入口 
-  人工支持入口（如果后面有） 
这类推荐非常重要，因为它能把“答不上来”转成“有效分流”。

---
场景 F：用户完成一个任务，准备离开
比如：
-  得到了明确答案 
-  点击了文档引用 
-  停留结束 
-  对话结束 
这个阶段适合推：
-  “你可能还想了解” 
-  “本周新功能” 
-  “相关产品案例” 
-  “继续提问建议” 
它更偏留存与功能发现，不要太强转化。

---
三、什么方式推荐给用户最合适
通过右侧 ChatPanel 的 ChatKit UI 来推荐，我建议不要只用一种形式，而是做成四种推荐载体，按场景切换。
1）轻提示型
最弱打扰，适合冷启动和新功能曝光
表现：
-  一条浅色信息条 
-  一句文案 + 一个按钮 
适用：
-  首次进入 
-  新功能发布 
-  当前页相关提示 

---
2）对话卡片型
最适合会话中推荐，是主力形态
表现：
-  像一条系统消息，但视觉上区别于 AI 回答 
-  包含标题、描述、按钮、可关闭、可反馈“不感兴趣” 
适用：
-  回答后推荐 
-  错配产品推荐 
-  功能推荐 
-  救场推荐 
这个应该成为你的核心 UI。

---
3）行动按钮型
最适合承接“下一步”
表现：
-  回答底部 1～3 个 chips 
-  如“查看相关产品”“体验语义搜索”“查看安装章节” 
适用：
-  回答完成后的即时行动引导 

---
4）阶段性浮层/强化卡片
只在高价值时机使用
表现：
-  比普通卡片更明显，但不遮挡输入 
-  有明确 CTA 
适用：
-  用户强意向选型 
-  高价值新功能灰度 
-  连续追问后强相关推荐 
这类一定要少用，建议只在高置信度和高价值场景触发。

---
四、推荐系统要具备哪些功能
1）运营后台配置能力
后台至少要支持这些字段：
推荐内容基础信息
-  推荐 ID 
-  类型：产品 / 功能 
-  标题 
-  副标题 
-  描述 
-  图标/封面 
-  CTA 文案 
-  跳转地址 
-  支持语言 
-  生效时间 / 失效时间 
-  状态：草稿、灰度、上线、下线 
定向条件
-  面向哪些产品线用户 
-  面向哪些页面 
-  面向哪些语言 
-  面向新用户/老用户 
-  面向哪些提问意图 
-  面向哪些关键词主题 
-  面向哪些行为阶段 
-  是否只在某版本功能发布期内显示 
触发规则
-  在回答前 / 回答后 / 连续追问后 / 无结果时 
-  最低置信度门槛 
-  最低相关度门槛 
-  每用户每日最多展示次数 
-  同一推荐的冷却时间 
-  黑名单场景（故障/投诉/危险操作时不推） 
策略控制
-  优先级 
-  是否参与实验 
-  实验组比例 
-  人群包配置 
-  是否允许个性化排序 
数据回收
-  展现量 
-  点击量 
-  关闭量 
-  转化量 
-  二跳行为 
-  推荐后提问变化 

---
2）推荐决策引擎
这部分是“大脑”。
它不是简单“后台配置了就展示”，而是需要根据上下文算出“现在该不该推、推哪个”。
输入建议包括：
-  当前页面 
-  当前产品线 
-  当前语言 
-  当前对话内容 
-  Triage Agent 识别的产品/意图 
-  Support Agent 的回答状态 
-  检索质量 
-  用户历史行为 
-  近期是否已被推荐过 
-  当前会话阶段 
输出：
-  是否推荐 
-  推荐哪个内容 
-  用什么形式推荐 
-  在回答前还是回答后推荐 
-  展示优先级 

---
3）用户行为与画像模块
先不用做复杂用户画像，第一阶段做轻量版就够了。
建议先记录：
-  会话级行为：本轮提问、产品归属、意图、检索命中、回答满意度 
-  用户级行为：最近看过哪些产品、点过哪些推荐、对哪些功能感兴趣 
-  推荐级行为：曝光、点击、关闭、忽略、转化 
这样你很快就能从“规则推荐”走到“轻量个性化推荐”。

---
4）前端推荐渲染模块
就在 ChatPanel 中新增推荐位组件。
建议做成统一组件：
- RecommendationCard
- RecommendationChips
- RecommendationBanner
由后端返回结构化 recommendation payload，前端只负责渲染，不自己判断推荐逻辑。

---
5）数据分析和实验能力
推荐系统上线后，一定要能回答四个问题：
-  哪些推荐最有效 
-  哪些触发时机最好 
-  哪些用户群更容易转化 
-  推荐是否打扰了问答体验 
所以要有：
-  曝光/点击埋点 
-  A/B 实验 
-  频控分析 
-  负反馈分析 
-  推荐对会话完成率、继续提问率的影响分析 

---
五、真正的推荐逻辑应该怎么做
不建议一开始上复杂算法。最合理的路径是：
第一阶段：规则驱动
适合快速落地。
核心规则示例：
规则 1：当前问题与当前产品不匹配
-  用户在 Aegis EDU 页面 
-  问题语义命中 Aegis Ultra 能力词 
-  则推荐相关产品卡 
规则 2：回答后推荐下一步功能
-  问题属于“搜索/导航/查找” 
-  回答后推荐“语义搜索”“引用跳转” 
规则 3：连续追问同一主题
-  3 轮内主题相似度高 
-  则推荐专题功能或更适配产品 
规则 4：检索失败
-  citation 少 / 相关度低 / 回答降级 
-  则推荐通用支持或替代产品 
规则 5：新功能灰度曝光
-  命中目标用户 
-  会话前 1 次轻推荐 
-  7 天内最多 2 次 
这套规则先跑起来，最稳。

---
第二阶段：上下文评分排序
在规则之上加打分。
每条推荐可以有一个综合分：
Score = 场景匹配度 × 内容相关度 × 用户兴趣度 × 业务优先级 × 新鲜度 - 打扰成本
其中：
-  场景匹配度：当前时机是否合适 
-  内容相关度：和问题、页面、产品是否强相关 
-  用户兴趣度：用户最近是否看过类似内容 
-  业务优先级：后台配置的权重 
-  新鲜度：新功能上线初期加权 
-  打扰成本：近期是否推过太多次 
这样就不是“命中规则即展示”，而是“命中后排序展示”。

---
第三阶段：个性化优化
等有一定数据后，再加个性化。
比如：
-  经常看 EDU 内容的用户，优先推教育场景能力 
-  经常点击功能类推荐的用户，少推产品，多推功能 
-  经常忽略推荐的用户，降低频率，改成更轻形式 
这时可以加简单模型，但没必要一开始就上复杂推荐算法。

---
六、什么时候不要推荐
这是很多团队会忽略的点。
以下场景建议默认抑制推荐：
-  用户正在进行故障排查 
-  用户连续表达负面情绪 
-  涉及安全、风险、错误操作 
-  回答仍未完成，用户焦虑明显 
-  短时间已连续看到多个推荐 
-  用户主动关闭过同类推荐 
因为在这些时刻，推荐会损伤信任。

---
七、结合你现有架构，怎么实现最顺
你当前系统已经有多 Agent 路由、ChatKit 后端、前端 ChatPanel，所以实现路径很明确：在现有问答链路旁边插入一个Recommendation Service。现有问答能力来自 ChatPanel、/chatkit、Triage Agent 与 Support Agent，这正好给推荐系统提供了最关键的上下文。
建议的新架构
前端
- ChatPanel.tsx 增加推荐消息渲染能力 
-  增加埋点上报：曝光、点击、关闭、忽略 
-  增加 recommendation slot 管理 
-  支持 system card / chips / banner 三种展示形式 
后端
新增一个推荐域服务，建议放在 rag_server 内，先不拆独立服务：
- recommendation_controller
- recommendation_service
- recommendation_rule_engine
- recommendation_ranker
- recommendation_repository
- recommendation_event_tracker
配置后台
单独做一个 Admin：
-  推荐内容管理 
-  触发规则管理 
-  人群定向管理 
-  实验管理 
-  数据看板 
数据层
至少需要 4 类表：
1. reco_campaign
  -  推荐活动/内容定义 
2. reco_targeting_rule
  -  定向和触发规则 
3. reco_delivery_log
  -  每次给谁展示了什么 
4. user_interest_profile
  -  用户兴趣标签和偏好统计 

---
八、推荐系统在问答链路中的插入点
我建议插两个点，一个“前置判断”，一个“后置增强”。
插入点 1：Triage 后
流程变成：
用户提问
 → Triage Agent 做语言、产品识别、查询扩写
 → Recommendation Engine 读取 triage 结果
 → 判断是否需要预推荐
 → Support Agent 继续回答
这一步适合做：
-  产品错配纠偏 
-  冷启动导流 
-  无明确产品时的分流 

---
插入点 2：Answer 后
流程变成：
Support Agent 生成回答
 → 检索质量、回答类型、意图标签返回
 → Recommendation Engine 决策
 → 在 ChatKit 流里附加 recommendation payload
 → 前端渲染推荐卡
这一步适合做：
-  回答后的下一步推荐 
-  功能发现 
-  相关产品推荐 
-  检索失败兜底 
这个插入点是最重要的主链路。

---
九、推荐消息的数据结构建议
前后端之间建议统一结构化协议，比如：
{
  "recommendations": [
    {
      "id": "reco_123",
      "type": "feature_reco",
      "placement": "after_answer",
      "ui_mode": "card",
      "title": "试试语义搜索",
      "description": "你可以直接搜索问题关键词，快速定位相关手册内容。",
      "cta": {
        "label": "立即体验",
        "action": "open_search"
      },
      "priority": 85,
      "dismissible": true,
      "tracking": {
        "impression_id": "imp_xxx"
      }
    }
  ]
}
这样前端和策略解耦，后续想改 UI，不影响推荐引擎。

---
十、一个最实用的推荐策略蓝图
我建议先定义 6 个固定推荐场景，每个场景只允许 1 条推荐，避免泛滥。
场景 1：新用户首次打开 ChatPanel
推：
-  热门提问 
-  使用引导 
-  新功能轻提示 
场景 2：产品识别不明确
推：
-  产品选择建议 
-  你可能想看的机器人产品 
场景 3：问题和当前产品错配
推：
-  更匹配的机器人产品 
场景 4：回答完成
推：
-  相关功能点 
-  下一步入口 
-  相关文档 
场景 5：连续追问
推：
-  专题页 
-  深层功能 
-  高阶产品 
场景 6：回答低置信度或无结果
推：
-  替代产品 
-  通用支持 
-  相关入口 
先把这 6 个做好，基本就已经是一个完整产品了。

---
十一、运营后台应该怎么设计
后台建议分 5 个页面：
1. 推荐内容库
管理所有产品/功能推荐内容
2. 触发策略中心
配置“什么场景触发什么推荐”
3. 人群与定向
配置按产品、页面、语言、用户类型做定向
4. 实验中心
支持 A/B 测试、灰度发布、回滚
5. 数据分析看板
看曝光、点击、转化、负反馈、会话影响
其中最关键的是策略中心，不是内容库。

---
十二、效果指标怎么定义
不要只看 CTR，要分层看。
推荐效果指标
-  曝光率 
-  CTR 
-  关闭率 
-  转化率 
-  推荐后继续提问率 
问答体验指标
-  会话完成率 
-  回答满意度 
-  用户停留时长 
-  推荐后打断率 
-  推荐后退出率 
业务指标
-  产品页导流率 
-  新功能使用率 
-  跨产品转化率 
-  老用户功能发现率 
如果 CTR 高但会话满意度下降，说明推荐打扰太强。

---
十三、最合理的落地路径
Phase 1：1 个月内可落地的版本
先做规则型、可配置、低打扰推荐。
包括：
-  后台配置推荐内容 
-  ChatPanel 支持 recommendation card 
-  回答后推荐 
-  错配产品推荐 
-  检索失败兜底推荐 
-  基础埋点和频控 
这是最值得先上的版本。

---
Phase 2：增强版
-  加连续追问识别 
-  加用户兴趣标签 
-  加多样化排序 
-  加实验系统 
-  加新功能灰度投放 

---
Phase 3：智能化版
-  做上下文评分排序 
-  做个性化频控 
-  做推荐文案动态生成 
-  做不同用户群差异化推荐

这个推荐系统最正确的产品定义，不是“在 ChatPanel 里加广告位”，而是：
在用户问答过程中，基于当前问题、当前产品、回答结果和行为状态，实时决定是否推荐某个产品或新功能，并通过低打扰的会话卡片形式进行呈现。
它的最佳落地方式是：
- 前端：在 ChatPanel 增加推荐卡/按钮渲染 
- 后端：在现有 ChatKit + Agent 链路旁增加 Recommendation Engine 
- 后台：建立可配置的推荐运营台 
- 策略：先规则，后排序，再个性化 
- 时机：以“回答后推荐”为主，“错配纠偏”和“无结果兜底”为高价值补充 
- 原则：强相关、低打扰、有频控、可关闭、可实验 
基于现有的系统结构，这条路径是最顺的，因为它直接复用现有的 ChatPanel、ChatKit、Triage Agent、Support Agent 和后端服务层，不需要重做主架构。
