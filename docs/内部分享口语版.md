# Claude Code 的核心逻辑，以及它和 OpenAI Agent Builder、Google ADK 到底有什么不同

大家好，今天这次分享，我想聊一个我最近一直在看的话题，就是 `Claude Code` 的核心处理逻辑。

我为什么会想讲这个题？  
因为我们现在项目里在用 `Agent Builder`，之前我也在别的项目里用过 Google 的 `ADK`。最近再去看 `Claude Code`，我会发现一件事：这三个东西都叫 Agent 相关能力，但它们脑子里默认的“系统长什么样”，其实很不一样。

所以我今天想回答三个问题：

1. 我们平时把 `Claude Code` 理解成一个 loop，这个理解到底对不对？
2. 如果这个理解不够完整，那 `Claude Code` 更准确的核心逻辑应该怎么描述？
3. 它和 `OpenAI Agent Builder`、`Google ADK` 在“核心处理”上，到底差在哪里？

---

## 先说结论

我先把结论放前面，后面再慢慢展开。

第一个结论：  
把 `Claude Code` 理解成一个 loop，这个方向是对的，但这个说法还不够。

更准确一点讲，`Claude Code` 不是“一个 prompt 进来，调个 tool，再继续 prompt”的简单循环。  
它更像一个**以 LLM 决策为中心的 agentic loop**，外面再包了一层：

- `memory`，决定每次思考时带哪些背景
- `hooks`，决定这个过程怎么被治理和约束
- `tools / MCP / skills`，决定它到底能做什么
- `permissions / stop`，决定哪些动作能执行、什么时候这一轮真正结束

第二个结论：  
这三套东西虽然都和 Agent 有关，但它们的第一抽象不一样。

- `Claude Code` 更像一个已经做好的、能直接工作的自治式 coding agent
- `OpenAI Agent Builder` 更像一个可视化工作流编排平台
- `Google ADK` 更像一个显式的 agent runtime 框架

我觉得这句话非常关键，因为后面所有区别，本质上都是从这里长出来的。

---

## 第一部分：我原来对 Claude Code 的理解，哪些是对的

我先把我一开始的理解复述一下，大概是这样：

> Claude Code 的核心就是一个 loop。拿到用户 prompt 以后，进入 loop，通过 LLM 分析，调用触发的 tools 或者 skill，拿到结果以后，再次进行 LLM 分析，直到触发 stop，退出 loop。

这个理解里，**主干是对的**。

为什么说它对？  
因为 `Claude Code` 的确不是传统 chatbot 那种“一问一答，然后结束”的模式。  
它更像这样一个过程：

1. 先看当前上下文
2. 决定下一步要干什么
3. 如果需要，就去调用工具
4. 把工具返回的结果放回来
5. 再判断下一步
6. 直到当前回合完成

所以从这个意义上讲，`Claude Code` 确实是一个 loop，而且是一个多步 loop。

这点特别重要。  
因为它说明 `Claude Code` 的核心不是“生成一段文本”，而是“围绕一个任务不断决策和执行”。

换句话说，它不是只负责“说”，它还负责：

- 读项目
- 找信息
- 触发工具
- 执行动作
- 看结果对不对
- 再决定下一步

这就是它和普通聊天机器人的根本区别。

## 第二部分：但这个理解还不够，哪里需要纠偏

我觉得主要有五个地方需要纠偏。

### 第一，`skill` 不是 loop 里每轮都固定经过的一环

很多人第一次看 `Claude Code`，会很容易把 `skill` 和 `tool` 放在同一层来理解。  
但如果仔细看官方文档，其实不是这么回事。

`tool` 更像什么？  
更像“模型可以调用的动作能力”。

比如：

- 读文件
- 搜代码
- 执行命令
- 调外部 MCP 工具

那 `skill` 更像什么？  
更像一个任务套路，或者一套工作说明。

也就是说：

- `tool` 解决的是“能不能做”
- `skill` 解决的是“这类任务怎么更稳、更规范地做”

所以如果我们要更准确地描述主循环，我觉得应该这么说：

> 用户输入进来以后，模型先根据当前上下文做决策，然后决定是直接回答，还是读取更多上下文，还是调用工具，还是按需激活某个 skill。接着把新结果再放回上下文，进入下一轮决策。

这里的重点是：  
`skill` 不是每轮必走，它更像按需装载的能力包。

### 第二，`memory` 不等于“每轮新数据都会变成长期记忆”

这一点我觉得特别容易说混。

如果只从 loop 的角度去想，很容易把 `memory` 理解成：

> 每转一圈，新的内容都加入系统记忆，所以下一轮 prompt 会越来越长。

这个说法只能说对了一半。

更准确一点，我觉得应该把 `Claude Code` 的“记忆”拆成两层。

第一层，是**会话内上下文**。

比如：

- 用户刚说的话
- 这轮读到的文件内容
- 上一轮工具的执行结果
- MCP 返回的数据
- 中间压缩出来的摘要

这些东西确实会进入下一轮模型调用，所以“每轮新数据会进入下次 prompt”这个说法，在会话内是成立的。

但是第二层，是**跨会话记忆**。

这时候就不是“所有聊天历史自动永久保存”这么简单了。  
它更多依赖这些机制：

- `CLAUDE.md`
- `CLAUDE.local.md`
- `.claude/rules/`
- auto memory

官方文档其实讲得很明确：  
**每个新 session 都是从一个新的 context window 开始**。

这句话非常关键。  
它意味着：`Claude Code` 并不是天然把上一次聊天全文带入下一次会话。

所以如果我要把这件事讲清楚，我会这么说：

> Claude Code 的 memory，不是“聊天记录无限累积”，而是“当前会话上下文 + 项目/用户级持久说明 + 自动沉淀记忆”的组合。

### 第三，`stop` 不是只有“模型觉得说完了”

如果只用大模型的视角去理解，stop 很容易被想成：

- 模型不再调工具
- 模型输出一段最终答案
- 当前回合结束

但 `Claude Code` 的 stop 更像一个运行时生命周期点。

也就是说，结束当前回合，不只是模型自己说一句“我好了”。

它背后至少还包括这些情况：

- 模型自然结束当前回复
- `Stop` hook 被触发
- hook 可以允许结束，也可以阻断结束并要求继续
- 用户也可能手动中断
- 如果 API 出错，还会走 `StopFailure`

所以 `stop` 更接近什么？  
更接近“当前 turn 的结束判定”，而不是“模型停止生成”这么简单。

### 第四，`hook` 不只是一个加工函数，而是治理层

我们平时讲 hook，容易讲成：

> 在输入和输出前后做一些固定处理。

这个理解当然不能说错，但它把 hook 说小了。

如果从架构视角看，我会更愿意把 `hook` 讲成：

> `Claude Code` 的确定性治理机制

为什么这么说？  
因为它不是只改一下字符串，而是可以在多个生命周期点介入，比如：

- `UserPromptSubmit`
- `PreToolUse`
- `PostToolUse`
- `PostToolUseFailure`
- `Notification`
- `Stop`

这意味着什么？

意味着 `Claude Code` 虽然整体上是一个由 LLM 驱动的自治 loop，但它外面其实包着一层可控的、规则化的治理平面。

所以如果我在分享里要讲 hook，我会用一句话概括：

> LLM 负责“想”，tools 负责“做”，hooks 负责“管”。

### 第五，`状态更新` 这个点要换个更准确的说法

你原来提到一个点，我觉得很有价值，就是：

> 在 loop 里面每次 LLM 之后，调用 MCP 或者 skill 的时候都会通知当前执行状态。

这个观察方向是对的，但如果用更官方、更工程化的说法，我觉得应该改成：

> Claude Code 在 agentic loop 中存在一整套生命周期事件、权限判定和执行状态反馈机制。

为什么我要这样改？

因为它不是只有“通知一下状态”这么轻。

更准确地看，它至少包括：

- 工具调用前的拦截
- 工具调用后的结果反馈
- 权限请求与批准
- 通知事件
- 停止事件

所以这部分如果写成“状态更新机制”，听众会以为只是 UI 层消息。  
但如果写成“生命周期治理与执行反馈”，就更接近它本来的角色。

## 第三部分：那 Claude Code 的核心逻辑到底该怎么讲

如果让我用一句比较准确的话定义 `Claude Code`，我会这么说：

> Claude Code 的核心不是单一的模型循环，而是一个以模型决策为中心的 agentic loop。这个 loop 在每一轮中结合当前上下文做出下一步决策，按需调用本地工具、MCP 工具或技能，并通过 hooks、权限机制和记忆系统对执行过程进行治理，直到当前回合满足结束条件。

如果再口语一点，我会这么讲：

> Claude Code 本质上是一个会持续“看上下文、做决策、调能力、收结果、再决策”的系统。它不是只靠模型裸跑，而是把模型放在一个完整的运行时里面。

我个人很喜欢把它拆成四层来讲，这样听众一下就能明白。

### 第一层，决策层：LLM

这一层负责判断：

- 用户现在到底想完成什么
- 还缺什么信息
- 下一步是回答，还是查，还是执行
- 要不要继续拆分任务
- 当前回合能不能结束

所以大模型在这里不是“写答案机器”，而是“下一步决策器”。

### 第二层，能力层：Tools / MCP / Skills

这一层回答的是：它到底能做什么。

这里面包括：

- 本地工具
- `MCP`
- `skills`

从架构上说：

- `tools` 是动作能力
- `MCP` 是外部能力扩展接口
- `skills` 是任务套路和工作流模板

### 第三层，治理层：Hooks / Permissions / Status

这一层回答的是：它怎么安全、可控地做。

比如：

- 这次工具调用要不要拦
- 要不要用户批准
- 某些动作能不能被禁止
- 执行过程中展示什么状态
- 当前回合到底能不能真的结束

这一层的存在非常重要。  
因为如果没有它，Claude Code 就只是一个“会调工具的大模型”。  
有了这一层，它才像一个真正能进工程环境的 agent runtime。

### 第四层，记忆层：Context / CLAUDE.md / Auto memory

这一层回答的是：每次决策时，它脑子里到底带了什么背景信息。

这里至少包括：

- 当前会话上下文
- 项目级说明
- 用户级偏好
- 长期沉淀记忆

所以到这里我们其实就能看出来了：

> Claude Code 不是“一个 loop”这么简单，而是“一个以 loop 为主干、以 memory 为上下文底座、以 hooks 为治理机制、以 tools/MCP/skills 为能力扩展的 agent runtime 产品”。

## 第四部分：如果把 Claude Code 的运行过程讲给团队听，我会怎么讲

我觉得可以用一个非常适合口头讲解的 8 步版。

### 第一步，先装载上下文

一个新的会话开始以后，Claude Code 不是从零开始。  
它会先加载一批背景信息，比如：

- 当前工作目录
- 项目里的 `CLAUDE.md`
- 用户自己的 `CLAUDE.local.md`
- `.claude/rules/`
- auto memory 摘要
- 当前可用的工具和技能描述

所以它其实是先把“工作环境”准备好，再开始处理你的输入。

### 第二步，接收用户输入

用户输入进来以后，也不一定是立刻原封不动地送给模型。  
它有可能先经过 `UserPromptSubmit` 这样的 hook。

这一步说明什么？  
说明系统对“输入进入模型之前”这件事，本身也是可治理的。

### 第三步，模型做决策

接下来模型要判断：

- 直接回答行不行
- 要不要读文件
- 要不要调用工具
- 要不要调 MCP
- 要不要激活某个 skill
- 要不要继续拆任务

我觉得这一阶段是整个系统的大脑。

### 第四步，执行工具或外部能力

如果模型决定要调用工具，就进入执行阶段。

这个阶段通常不是直接无脑执行，而是会经历：

- `PreToolUse`
- 权限判断
- 实际执行
- `PostToolUse`
- 或者失败时走 `PostToolUseFailure`

所以 tool call 不是一个点动作，而是一条受运行时管理的链路。

### 第五步，把结果写回上下文

工具结果回来以后，不管它来自：

- 本地工具
- `MCP`
- 文件读取
- skill 相关过程

最终都要重新进入当前上下文，供下一轮决策使用。

这一步其实就对应你原来理解里最核心的那句：

> 每轮都会产生新数据，这些数据会进入下一次 LLM 的 prompt

这句话在当前 session 内是成立的。

### 第六步，再做一次决策

拿到新结果以后，模型会继续判断：

- 信息够不够
- 还要不要继续查
- 还要不要继续执行
- 需不需要验证一下
- 现在能不能结束

所以 Claude Code 的 loop，本质上就是：

`决策 -> 执行 -> 回写 -> 再决策`

### 第七步，必要时整理上下文

会话一长，上下文一定会膨胀。  
这个时候系统要做的事情，不是机械地一直往 prompt 里追加。

它还会涉及：

- 摘要
- 压缩
- 保留关键内容
- 让长期内容通过记忆文件继续存在

所以它的 memory 机制本质上不是“加法”，而是“筛选 + 保留 + 持久化”。

### 第八步，满足条件后结束当前 turn

当前回合什么时候结束？

大体上是在这些条件满足的时候：

- 模型认为当前任务已经完成
- 不再需要新的工具调用
- `Stop` 生命周期允许结束
- 没有用户中断或错误打断

所以 stop 更准确的理解是：

> 当前 turn 的完成判定

而不只是：

> 模型结束生成

## 第五部分：那它和 OpenAI Agent Builder 到底差在哪

讲到这里，我们再来看 `OpenAI Agent Builder`。

我自己觉得，最重要的一句话是：

> `Claude Code` 强调的是“自治执行”，`Agent Builder` 强调的是“可视化编排”。

这两个方向看起来都在做 Agent，但底层脑回路完全不一样。

### Agent Builder 最核心的抽象是什么

OpenAI 官方对它的定义其实很直白：  
它是一个 **visual canvas for building multi-step agent workflows**。

我觉得这里最关键的是 `workflow` 和 `canvas` 这两个词。

因为这说明 Agent Builder 首先在解决的问题不是：

- agent runtime 内部怎么运转
- 一个 coding agent 如何自治完成任务

它最先解决的是：

> 我怎么把 agent、tool、logic、state 组织成一个工作流，并且把它发布出去

所以你会看到它强调的是：

- `Start`
- `Agent`
- `MCP`
- `Guardrails`
- `If/else`
- `While`
- `Human approval`
- `Set state`

这整套东西都在说明：  
它的第一抽象是 **workflow graph**。

### 它和 Claude Code 最大的不同在哪

我觉得有三个点特别值得讲。

#### 第一，循环的来源不一样

在 `Claude Code` 里，循环更多是系统内部自带的 agentic loop。  
在 `Agent Builder` 里，循环更多是开发者显式画出来的 `While` 节点。

也就是说：

- `Claude Code`：系统自己会 loop
- `Agent Builder`：你来定义哪里 loop、怎么 loop、何时停止

#### 第二，状态的表达方式不一样

`Agent Builder` 里，状态是非常 workflow 化的。  
比如 `Set state` 就是在定义全局变量，供整个工作流使用。

这个思路非常像传统工作流系统。

而 `Claude Code` 更强调的是：

- 当前上下文
- 项目级说明
- 长期记忆
- 当前会话中不断回写的新信息

两者都在处理“状态”，但抽象方式完全不同。

#### 第三，可观测性的重点不一样

OpenAI 在这方面的主线非常清晰：

- trace
- trace grading
- preview
- evaluate

也就是说，它天然把 agent workflow 当成一个：

- 可观察
- 可评估
- 可优化
- 可版本化

的流程资产。

这一点和 `Claude Code` 也很不一样。  
`Claude Code` 更强调“把事做成”，`Agent Builder` 更强调“把流程编出来、跑出来、看得见、评得动”。

所以如果让我一句话总结：

> `OpenAI Agent Builder` 的核心不是通用自治 loop，而是节点化、类型化、可发布的 agent workflow 编排系统。

## 第六部分：那 Google ADK 又有什么不一样

接下来再看 `Google ADK`。

我自己对 ADK 的感觉是：

> 它不是在先给你一个产品，而是在先给你一套 runtime 骨架。

这件事很重要。

因为你一看 ADK 的核心词汇就知道，它脑子里想的不是产品页面，而是运行时结构：

- `Runner`
- `Event Loop`
- `Event`
- `Session`
- `State`
- `MemoryService`
- `Callbacks`
- `Workflow Agents`

### ADK 最核心的东西是什么

如果让我挑一个关键词，我会选 `Runner + Event Loop`。

为什么？

因为 ADK 的基本叙事是这样的：

1. Runner 收到用户请求
2. Agent 开始执行
3. 执行过程中不断产出 `Event`
4. Runner 处理这些 event，并提交相应状态变化
5. 然后 Agent 再继续往下跑
6. 直到没有新的 event

所以它的核心不是“有个模型会不会自己继续想”，而是：

> 有一个显式的运行时在驱动 agent、tool、callback 和状态提交

这一点和 `Claude Code` 有点像，但又不一样。

像的地方在于，它们都不是单轮聊天。  
不一样的地方在于：

- `Claude Code` 更像把 runtime 封装好了给你直接用
- `ADK` 更像把 runtime 机制打开给你自己搭

### ADK 的 state 和 memory 为什么更“框架化”

我觉得 ADK 在这方面的表达非常典型，像一个成熟框架。

它会明确区分：

- `Session`：当前对话线程
- `State`：当前 session 内部数据
- `Memory`：跨 session 的长期知识
- `MemoryService`：长期记忆的管理器

你会发现这种表达和 `Claude Code` 不太一样。

`Claude Code` 当然也有记忆和上下文，但它的文档更偏产品说明。  
ADK 则更像在告诉你：

> 这是框架运行时里的正式契约，你可以围绕这些抽象自己搭系统

### ADK 的 callbacks 和 Claude Code hooks 有什么不同

这两个概念很像，但我觉得讲的时候最好不要直接划等号。

因为它们的重心不同：

- `Claude Code hooks` 更像产品生命周期里的治理点
- `ADK callbacks` 更像框架执行链路中的可编程回调点

ADK 的 callbacks 可以挂在：

- `Before Agent`
- `After Agent`
- `Before Model`
- `After Model`
- `Before Tool`
- `After Tool`

而且它的返回值会真的影响后面的控制流。  
所以它更像 runtime 层暴露给开发者的一套程序化插桩机制。

### 一个特别容易混淆的点：`LoopAgent`

这个点我建议在分享时一定单独强调一下。

为什么？  
因为大家一听到 loop，就很容易说：“那 ADK 不是也有 loop 吗？”

是，但不是一回事。

`ADK` 里的 `LoopAgent` 是一个开发者显式定义的 workflow primitive。  
它的意思是：你可以造一个循环型 agent，让它反复跑自己的子 agent。

但 `Claude Code` 的 loop 不一样。  
它是整个系统默认的主执行方式。

所以我会这样讲：

- `Claude Code loop`：系统级 agentic loop
- `ADK LoopAgent`：框架里一个可选的循环编排组件

这两个“loop”不是一个层级上的概念。

所以如果要一句话总结 ADK，我会说：

> `Google ADK` 的核心不是一个现成 agent 产品，而是一套显式的、事件驱动的 agent runtime 框架。

---

## 第七部分：三者真正的本质区别，到底是什么

讲到这里，其实就能收束出最关键的观点了。

三者最大的区别，不在于它们是不是都有：

- tool
- memory
- hook
- callback
- loop

而在于：

> 它们默认把“系统的中心”放在哪里

我觉得可以这么理解。

### `Claude Code` 的第一抽象：自治执行

它最先回答的问题是：

> 怎么让一个 coding agent 在真实项目环境里自己把事做起来？

所以它天然强调：

- agentic loop
- 文件与终端能力
- MCP 扩展
- hooks 治理
- 项目说明与长期记忆

### `OpenAI Agent Builder` 的第一抽象：工作流编排

它最先回答的问题是：

> 怎么把 agent、tool、logic、state 组织成一个可视化、可发布、可评估的工作流？

所以它天然强调：

- canvas
- nodes
- typed edges
- `While`
- `If/else`
- trace
- publish / deploy

### `Google ADK` 的第一抽象：运行时机制

它最先回答的问题是：

> 怎么给开发者一套清晰的 runtime、event、state、memory、callback 机制，让他自己搭 agent 系统？

所以它天然强调：

- Runner
- Event Loop
- Session / State / MemoryService
- Workflow Agents
- Callbacks

所以如果一定要用一句特别短的话来总结，我会这么说：

- `Claude Code`：产品化的自治型 agent
- `Agent Builder`：工作流即系统
- `ADK`：运行时即系统

---

## 第八部分：如果我现场只讲 2 分钟，我会怎么收尾

我最后会用下面这段话来收口。

我一开始把 `Claude Code` 理解成“一个 loop”，这个理解本身没有错，但不够完整。  
更准确地说，`Claude Code` 是一个以 LLM 决策为中心的 agentic runtime 产品：loop 负责推进任务，`tools` 和 `MCP` 提供能力，`skills` 封装可复用工作流，`memory` 提供持续上下文，`hooks` 负责治理和约束，`stop` 则定义这一轮什么时候真正结束。

如果把它和另外两套体系放在一起看，我觉得差异就更清楚了。

`OpenAI Agent Builder` 重点不是 runtime 内部细节，而是把 `agent`、`tools`、`logic`、`state` 编排成一个可发布的工作流。  
`Google ADK` 则更进一步，它直接把 `Runner`、`Event Loop`、`Session`、`Memory`、`Callbacks` 这些 runtime 机制暴露给开发者，让你自己搭系统。

所以三者虽然都叫 Agent，但其实站在三个不同重心上：

- `Claude Code` 更像一个已经能工作的 agent 产品
- `Agent Builder` 更像一个工作流编排平台
- `ADK` 更像一个 agent runtime 框架

如果我们把这个分层想清楚，再去选型、再去对比产品能力，其实很多问题就会更容易想明白。
