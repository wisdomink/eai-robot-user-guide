# RAG FAQ Acceleration - Final Implementation Design

## 1. 文档目标

本文档描述当前 FF Robot 用户手册 AI 问答系统的最终版优化方案。

本方案不按 MVP 缩减，不考虑开发量限制，目标是形成一个完整、可运营、可观测、可持续优化的问答加速系统。

系统目标：

```text
降低响应耗时
降低大模型调用成本
提升高频问题回答稳定性
沉淀标准问答资产
支持上下文问题改写
保留复杂问题 RAG 能力
支持运营审核和持续优化
```

---

## 2. 现有系统理解

当前系统是一个用户手册 H5 + AI 问答系统，产品形态包括：

```text
React SPA
Markdown 内容站
语义搜索
ChatKit 对话
多 Agent RAG
引用跳转
后台配置
聊天历史
日志查询
Docker / AWS 部署
```

因此，本方案不替代现有 RAG，而是在现有 RAG 前面增加：

```text
问题理解层
FAQ 命中层
语义缓存层
智能路由层
高频问题沉淀层
运营审核层
评测与观测层
```

## 4. 核心设计原则

## 4.1 FAQ 只保存上下文无关问题

正式 FAQ 中只能保存：

```text
单独一句话即可理解的问题
```

可以进入 FAQ：

```text
FF Master 怎么充电？
FF Aegis Ultra 如何连接 Wi-Fi？
机器人无法开机怎么办？
FF 91 2.0 如何开启某个功能？
```

不能直接进入 FAQ：

```text
它怎么充电？
这个怎么设置？
刚才那个支持吗？
上面说的第二个怎么操作？
```

上下文相关问题需要先改写为 standalone question。

---

## 4.2 原始问题和标准问题分离

系统必须同时保存：

```text
raw_question：用户原始问题
standalone_question：上下文改写后的完整问题
canonical_question：FAQ 标准问题
```

示例：

```text
raw_question:
那它怎么恢复出厂设置？

standalone_question:
FF Master 如何恢复出厂设置？

canonical_question:
FF Master 如何恢复出厂设置？
```

---

## 4.3 FAQ 命中必须带产品过滤

不能只靠语义相似度。

必须满足：

```text
product 一致
language 合理
intent 一致
similarity 达标
status = published
```

对于安全、维修、故障类问题，阈值要更高。

---

## 4.4 高频问题不能自动发布

高频问题只能进入：

```text
候选 FAQ
```

必须经过人工审核后才能进入：

```text
正式 FAQ
```

原因：

```text
RAG 答案可能错误；
用户问题可能有歧义；
答案可能涉及安全风险；
手册内容可能更新；
不同产品答案可能不同。
```

---

## 5. 完整问答流程

## 5.1 主流程

```text
用户提交问题
  ↓
读取 thread_id 对应最近 N 轮对话
  ↓
识别当前页面产品 product_context
  ↓
生成 normalized_question
  ↓
判断是否上下文相关
  ↓
如果上下文相关：
    生成 standalone_question
    如果无法改写：
        返回澄清问题
  ↓
进入 Semantic Router
  ↓
根据 route 决定处理路径
```

---

## 5.2 路由类型

| Route | 说明 | 处理方式 |
|---|---|---|
| faq_route | 高频标准问题 | 查 FAQ |
| manual_rag_route | 手册类复杂问题 | 走 RAG |
| troubleshooting_route | 故障排查 | 高阈值 FAQ，未命中走 RAG |
| safety_route | 安全/维修/警告类 | 不使用低置信缓存 |
| lead_capture_route | 购买/试驾/咨询 | 走留资 |
| compare_route | 产品对比 | 走 RAG 或结构化答案 |
| clarification_route | 指代不明 | 反问澄清 |
| unsupported_route | 超出范围 | 兜底回复 |
| smalltalk_route | 闲聊 | 轻量回复 |

---

## 5.3 FAQ 命中流程

```text
standalone_question
  ↓
Exact Match
  ↓ 未命中
Alias Match
  ↓ 未命中
Semantic Match
  ↓
阈值判断
  ↓
产品一致性判断
  ↓
风险等级判断
  ↓
返回标准答案
```

---

## 5.4 RAG 兜底流程

```text
FAQ 未命中
  ↓
Semantic Cache 未命中
  ↓
调用原有 /api/chatkit
  ↓
执行原有多 Agent RAG
  ↓
返回答案和引用
  ↓
写入 query_log
  ↓
可选写入 semantic cache
```

## 6. 上下文问题处理方案

## 6.1 上下文相关判断

如果问题包含以下词汇，优先判断为上下文相关：

```text
它
这个
那个
刚才
上面
前面
你说的
第二个
第三步
继续
还有呢
详细说说
怎么弄
支持吗
多少钱
```

但不能只靠规则，最终版本应该结合：

```text
规则判断 + 轻量模型判断 + 会话状态判断
```

---

## 6.2 问题改写

输入：

```text
最近 N 轮对话
当前用户问题
当前页面产品
当前已识别产品
```

输出：

```text
standalone_question
rewrite_confidence
resolved_product
need_clarification
```

示例：

```text
历史：
用户：FF Master 怎么连接 Wi-Fi？
助手：可以进入设置页选择 Wi-Fi 网络。

当前问题：
那恢复出厂设置在哪里？

输出：
{
  "standalone_question": "FF Master 恢复出厂设置在哪里？",
  "rewrite_confidence": 0.93,
  "resolved_product": "FF Master",
  "need_clarification": false
}
```

无法改写时：

```text
历史：
用户：FF Master 和 FF Aegis 有什么区别？
助手：两者定位不同。

当前问题：
那它怎么充电？

输出：
{
  "standalone_question": null,
  "rewrite_confidence": 0.31,
  "resolved_product": null,
  "need_clarification": true,
  "clarification_question": "你指的是 FF Master 还是 FF Aegis？"
}
```

---

## 6.3 改写 Prompt

```text
你是一个客服问答系统的问题改写模块。

任务：
根据最近的聊天上下文、当前页面产品和用户当前问题，把用户问题改写成一个不依赖上下文也能独立理解的问题。

要求：
1. 只补全上下文中明确出现的信息，不要编造。
2. 如果能明确产品名，要把产品名补充到问题中。
3. 如果用户当前问题已经完整，直接返回原问题。
4. 如果无法确定“它、这个、那个”指代对象，返回 need_clarification=true。
5. 不要回答问题，只做问题改写。
6. 输出 JSON。

输入：
最近聊天上下文：
{{history}}

当前页面产品：
{{page_product}}

用户当前问题：
{{raw_question}}

输出 JSON：
{
  "standalone_question": "",
  "rewrite_confidence": 0.0,
  "resolved_product": "",
  "is_context_dependent": true,
  "need_clarification": false,
  "clarification_question": ""
}
```

## 10.2 候选问题生成规则

候选 FAQ 入库条件：

```text
同一产品
同一语言
standalone_question 相似度 >= 0.84
7 天内出现次数 >= 5
不是纯上下文问题
不是个人信息问题
不是订单/工单私有问题
不是无意义闲聊
```

高风险问题可以入候选，但不能自动发布。

---

## 10.3 候选问题合并规则

当新问题进入 query_log 后：

```text
1. 生成 standalone_question embedding
2. 查询 faq_candidate collection
3. 如果 similarity >= 0.84：
     合并到已有 candidate
     count + 1
     更新 similar_questions
4. 如果未命中：
     新建 candidate
```

## 11. Semantic Cache 设计

## 11.1 缓存对象

语义缓存只缓存满足条件的答案：

```text
RAG 成功回答
有明确产品
有明确引用
不是高风险问题
不是个人化问题
不是订单/售后问题
用户反馈不是负面
```

---

## 11.2 缓存结构

```json
{
  "cache_key": "semantic_cache_xxx",
  "product": "FF Master",
  "standalone_question": "FF Master 如何连接 Wi-Fi？",
  "answer": "你可以进入设置页面...",
  "citations": [
    {
      "title": "Wi-Fi 连接",
      "url": "/ff-master/network/wifi"
    }
  ],
  "embedding_model": "text-embedding-xxx",
  "created_at": "2026-04-29T00:00:00Z",
  "expire_at": "2026-05-29T00:00:00Z"
}
```

---

## 11.3 语义缓存命中规则

普通问题：

```text
similarity >= 0.90
product 一致
language 一致
intent 一致
cache 未过期
```

安全/维修/故障问题：

```text
默认不使用 semantic cache
除非 FAQ 已人工审核发布
```

## 12. 阈值策略

## 12.1 FAQ 命中阈值

| 问题类型 | 阈值 |
|---|---:|
| 普通使用说明 | 0.88 |
| 参数查询 | 0.90 |
| 充电/维修/故障 | 0.92 |
| 安全警告 | 0.95 |
| 售前咨询 | 0.86 |
| 闲聊 | 不进 FAQ |

---

## 12.2 候选聚类阈值

| 场景 | 阈值 |
|---|---:|
| 同产品普通问题聚类 | 0.84 |
| 同产品故障问题聚类 | 0.88 |
| 跨产品聚类 | 不允许 |
| 上下文改写低置信问题 | 不聚类 |

---

## 12.3 上下文改写阈值

| 条件 | 处理 |
|---|---|
| rewrite_confidence >= 0.85 | 可进入 FAQ 匹配 |
| 0.60 <= rewrite_confidence < 0.85 | 可进入 RAG，不进入 FAQ |
| rewrite_confidence < 0.60 | 反问澄清 |

## 15. 答案返回策略

## 15.1 FAQ 答案格式

FAQ 命中后，不需要模拟大模型长篇生成，应该直接返回结构化答案：

```text
标准答案
来源链接
更新时间
必要提醒
```

示例：

```text
FF Master 可以通过充电底座进行充电。请将机器人正确放置在充电底座上，并确认底座已接通电源。

来源：FF Master 用户手册 / 充电说明
```

---

## 15.2 FAQ 与 RAG 的用户体验差异

用户不需要感知底层来源，但系统内部需要标记：

```text
answer_source = faq_exact
answer_source = faq_semantic
answer_source = semantic_cache
answer_source = rag
```

前端可以显示：

```text
来源：用户手册
```

而不是显示：

```text
来源：FAQ 缓存
```

刹车

处理规则：

```text

必须有人工审核；

不使用普通 semantic cache；
必要时提示联系官方支持。
```

## 21. 最终系统效果

完成后，问答系统会变成四层回答体系：

```text
第一层：FAQ 精确命中
  - 最快
  - 最稳定
  - 适合标准问题

第二层：FAQ 语义命中
  - 较快
  - 适合同义问法

第三层：Semantic Cache
  - 复用历史 RAG 答案
  - 降低重复模型调用

第四层：RAG / Agent
  - 处理复杂问题
  - 处理长尾问题
  - 处理组合推理问题
```

最终目标：

```text
高频问题 100ms~300ms 返回；
普通语义 FAQ 300ms~800ms 返回；
复杂 RAG 问题继续流式输出；
RAG 调用比例逐步下降；
FAQ 命中率逐步提升；
用户反馈驱动 FAQ 持续优化。
```

## 22. 最终结论

本项目不应该引入完整客服机器人框架重做系统，而应该在现有 RAG 前面增加一套完整的“问答加速与知识运营层”。

最终推荐架构是：

```text
Redis + Qdrant + GPTCache + Semantic Router + 现有 ChatKit/RAG
```

其中：

```text
Redis 负责低延迟和统计；
Qdrant 负责语义匹配和聚类；
GPTCache 负责历史答案复用；
Semantic Router 负责智能分流；
现有 RAG 负责复杂问题兜底；
Admin 后台负责人工审核和知识运营。
```

核心原则：

```text
正式 FAQ 只保存上下文无关问题；
上下文相关问题必须先改写；
高频问题只进候选库，不自动发布；
安全类问题高阈值、强审核；
所有命中都要可追溯、可观测、可回滚。
```
